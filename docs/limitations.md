# Current limitations

pg-sprite refuses a schema change at capability, ownership, design, environment, or
internal-invariant boundaries. Some refusals mean there is no online-safety problem for
the engine to solve and name the owner that should handle the work. This page explains the *mechanics* of each current refusal; the
complete support matrix — every operation and object type, tiered as
supported / planned / out of scope, with reasons — is
[capabilities.md](capabilities.md). These are current capability boundaries,
not escape hatches:

| Change | Current behavior |
| --- | --- |
| `DROP COLUMN`, `DROP CONSTRAINT`, `ALTER COLUMN ... DROP NOT NULL`, and `DETACH PARTITION` on `migrate --alter` | Refused with `destructive-change` (class `by-design`, exit 2) before any route runs the statement — native, safer sequence, `--force`, or copy-and-swap — and `--dry-run` ends in the same refusal verdict: each discards data or a guarantee the schema was providing, and pg-sprite does not infer that the loss is intended. `--allow-destructive SCHEMA.TABLE` (`Options.AllowDestructive` as a library caller) names the resolved table and runs the statement through every other gate as usual; its verdict carries `allowed_destructive: true` and the run logs one warning naming the table. A mismatched acknowledgement executes nothing and exits 1. It acknowledges only the loss: a forced type rewrite that also drops a column needs `--force` too. With `--desired` it is accepted only together with `--expect-fingerprint` and applies to a reviewed plan (see [What desired-state execution converges today](#what-desired-state-execution-converges-today)). It does not lift a `DROP INDEX` refusal on its own; it is the second acknowledgement a `DROP INDEX` under `--accept-blocking` needs (below). A statement that drops a column and adds one of the same name back is refused with the `alter-column-type-in-place` guidance: `ALTER COLUMN ... TYPE ... USING ...` keeps the values the drop would discard. A planner refusal of a drop (`replica-identity`, `dependent-view`, `cascading-drop`) keeps its own reason, since no acknowledgement lifts it. |
| Index builds on a partitioned parent | PostgreSQL cannot build an index concurrently at the parent level, and a plain build takes `ACCESS EXCLUSIVE` on the whole tree. A plain `CREATE INDEX` on a partitioned parent therefore runs as the partitioned index build: the parent's index is created with `ON ONLY`, each partition's index is built concurrently and attached, and the parent's index turns valid with the last attach. Each step commits on its own, the partitions are listed when the run starts, and an interrupted run is resumed by running the same statement again. The build needs a named index, no `IF NOT EXISTS`, no `TABLESPACE` (it would place the parent's index and not the partitions'), and a schema-qualified table; a unique index must contain the partition key of every partitioned table in the tree; one that does not is refused (`unsupported-statement`, `by-design`) before anything is created, in `--dry-run` too. It refuses a tree with a foreign table partition or a partition whose `DETACH PARTITION ... CONCURRENTLY` did not finish. pg-sprite never runs the blocking form as submitted: `--force` does not bypass that, and `migrate --accept-blocking` does not reach it either — it covers the single-relation `DROP INDEX` / `REINDEX` refusals. See [partitioned-index-build-design.md](partitioned-index-build-design.md). |
| `ADD CONSTRAINT ... USING INDEX` on a partitioned parent | PostgreSQL does not support adopting an existing index on a partitioned parent in any supported version. pg-sprite refuses before execution. |
| `ADD PRIMARY KEY` / `ADD UNIQUE` on a partitioned parent | `migrate --alter` runs a lone named `ADD CONSTRAINT name {PRIMARY KEY \| UNIQUE} (columns)` on a partitioned parent as the partitioned key build: each partition's unique index is built concurrently and given the constraint, then the parent's `ADD CONSTRAINT` adopts them in one brief transaction that builds nothing. Each step commits on its own, the partitions are listed when the run starts, and an interrupted run is resumed by running the same statement again. Refused with `unsupported-statement` and nothing executed: an unnamed constraint or one with `INCLUDE`, `NULLS NOT DISTINCT`, `DEFERRABLE`, `WITH (...)`, or `USING INDEX TABLESPACE` (`capability-boundary`); a key that lacks a partition key column (`by-design`); a parent that already has a primary key or another object under the name, or a primary key over a column that allows `NULL` (`environmental`, make the column `NOT NULL` first); a tree with a sub-partitioned partition (`capability-boundary`). The parent, nullable column, and tree refusals are refusals only while the run has changed nothing; once a partition's concurrent index build has begun, which commits before the partition's constraint does, the same stop is a failed verdict with the executor's code. A foreign table partition, a partition whose `DETACH PARTITION ... CONCURRENTLY` did not finish, a name a partition's index needs that something else holds, and a conflicting key on a partition end the run in a failed verdict with the executor's code instead, as they do for the partitioned index build. The dry run reports the shape, partition key, and sub-partitioned tree refusals; the parent and nullable column checks are read only under the build's lock, so for those the dry run reports `execute` and the apply refuses. `--force` never runs the blocking form: it meets the `unsupported-partitioned-parent` refusal. A key a desired file adds takes the same route: `diff` plans it schema-qualified as `partitioned-key-build` (an unnamed constraint carries the server's default name, and `--sql` prints it commented out), and `migrate --desired` runs it as the build with the same verdicts, a primary key over a nullable column after the `SET NOT NULL` the file implies. A desired key that lacks a partition key column, or on a tree with a sub-partitioned partition, refuses the whole plan before its first statement, in `migrate --desired --dry-run` too, so nothing planned ahead of it commits. A desired key the build does not carry (`INCLUDE`, `NULLS NOT DISTINCT`, `DEFERRABLE`, `WITH (...)`, `USING INDEX TABLESPACE`) stays refused with `unsupported-partitioned-parent`, and a live parent index under the key's name is dropped (a blocking drop, under `--accept-blocking`) rather than adopted. See [partitioned-index-build-design.md](partitioned-index-build-design.md#primary-key-and-unique-constraints). |
| `ADD PRIMARY KEY` / `ADD UNIQUE` with a storage parameter the online sequence cannot render | The online sequence builds the key's index with `CREATE UNIQUE INDEX CONCURRENTLY` and carries the key's `WITH (...)` parameters onto it, each name quoted and each value a quoted literal. A parameter it cannot render faithfully, one whose value is not a plain word, number, or string, contains a backslash, or whose name is namespaced, would be dropped or changed, so no sequence is built. Running the statement as written builds the index under `ACCESS EXCLUSIVE`, so it is refused as `rewrite-required` with the `unique-index-then-constraint` guidance. Build the index concurrently with the parameter, then attach it with `ADD CONSTRAINT ... USING INDEX`. |
| `ADD FOREIGN KEY ... NOT VALID` on a partitioned parent | PostgreSQL does not support this before version 18, so pg-sprite refuses it on versions 14–17. It is supported on version 18 and later. On 14–17, submit the foreign key without `NOT VALID` (next row). |
| `ADD FOREIGN KEY` on a partitioned parent | On PostgreSQL 14–17, `migrate --alter` runs a lone named `ADD CONSTRAINT name FOREIGN KEY (columns) REFERENCES schema.table (columns)` on a partitioned parent as the partitioned foreign key build: each partition is given the foreign key `NOT VALID` and validated while writes continue, then the parent's `ADD CONSTRAINT` adopts them in one brief transaction that validates nothing; that transaction also takes `ACCESS EXCLUSIVE` on the referenced table for its few milliseconds, since adopting drops each partition foreign key's own triggers there. Each step commits on its own, the partitions are listed when the run starts, and an interrupted run is resumed by running the same statement again. Refused with `unsupported-statement` and nothing executed: an unnamed foreign key, an unqualified referenced table, an `ON DELETE` column list, `ONLY`, or a repeated column (`capability-boundary`, in the dry run too); a parent that already has another constraint under the name or the same foreign key under another name (`environmental`); a partitioned, foreign, or view referenced table, or a sub-partitioned partition (`capability-boundary`). Those last two, read again under the build's lock, are refusals only before any partition got the foreign key; the dry run reads them from the catalog first and reports the same refusal. A row that breaks the foreign key, a name a partition's foreign key needs that another constraint holds, a conflicting foreign key on a partition, a foreign table partition, or an unfinished detach end the run in a failed verdict with the executor's code instead. On PostgreSQL 18 the ordinary `NOT VALID` then `VALIDATE` sequence runs. `--force` runs the plain statement as written, under the brief budgets. A foreign key a desired file adds to a partitioned parent takes the same route: `diff` plans it as the build on 14–17, with the referenced table qualified with the target schema, and `migrate --desired` runs it with the same verdicts, except that it reads the referenced table and the partition tree before any statement runs, so a referenced table or sub-partitioned partition the build refuses refuses the whole plan, and a foreign table partition or an unfinished detach stops it as a failed result, with nothing executed and no column the file also adds committed; one whose shape the build does not carry, such as an `ON DELETE` column list, is refused on 14–17 with `unsupported-partitioned-parent` (class `environmental`). See [partitioned-foreign-key-design.md](partitioned-foreign-key-design.md). |
| `DROP INDEX` and `REINDEX`, plain or `CONCURRENTLY` | `migrate` never runs index maintenance online-safely. The plain form is refused with `index-statement` and names its `CONCURRENTLY` idiom; the concurrent form is refused as already safe, so run it directly against the database. `migrate --accept-blocking SCHEMA.TABLE` runs a single-relation plain `DROP INDEX`, `REINDEX INDEX`, or `REINDEX TABLE` as-is under bounded budgets and exits 3 ([lock-budgeted-passthrough.md](lock-budgeted-passthrough.md)). A `DROP INDEX`, unique or not, also needs `--allow-destructive` naming the same table: without it the drop is refused with `destructive-change` (exit 2) before anything runs, and the detail lists the checks to make first — `idx_scan` is 0 on the primary and every replica over a full application cycle, no foreign key relies on the index, and nothing needs a unique index's guarantee. The refusal's `index_usage` carries the connected server's own evidence — `idx_scan`, `stats_reset`, `last_idx_scan` (PostgreSQL 16+), uniqueness, and whether `track_counts` was on — which covers that one server only, never its replicas. `diff`'s hint to run a removed index through `migrate --alter` ends in this refusal; on a plain table, run `DROP INDEX CONCURRENTLY` directly, or remove the index from the desired file and run the reviewed plan with `migrate --desired`, which drops it concurrently. An index of a partitioned table is the exception: PostgreSQL rejects `DROP INDEX CONCURRENTLY` for it in every supported version, and a partition's own index cannot be dropped alone. `diff` refuses such a drop with `unsupported-partitioned-parent` (class `by-design`, preflight cause `parent-concurrent-index-drop`), offers no concurrent rewrite, and carries the plain drop as its `blocking-index-drop` step; the drop is the plain `DROP INDEX` under `--accept-blocking SCHEMA.TABLE --allow-destructive SCHEMA.TABLE` — through `migrate --alter`, or from the reviewed plan through `migrate --desired` with `--expect-fingerprint` — which takes `ACCESS EXCLUSIVE` on the parent, every partition, and every partition's index while it runs ([command and verdict](lock-budgeted-passthrough.md#dropping-an-index-of-a-partitioned-table)). `migrate --alter` and its `--dry-run` read the index's kind from the catalog before refusing a single-index `DROP INDEX`, so they need a database connection for it: a partitioned index is refused in both forms with the same reason and cause and no `safer_idiom`, the accepted plain drop's verdict says every partition and partition index was locked, and the `CONCURRENTLY` form stays refused under the flags. A partition's index attached under a parent index is refused in either form, flags or not, as `unsupported-statement` (class `by-design`), naming the root partitioned index to drop instead. When the index it comes down to is owned by a primary key, unique, or exclusion constraint, the drop is refused the same way, naming the `ALTER TABLE ... DROP CONSTRAINT` that removes it. A role without `USAGE` on the index's schema gets the catalog-free `index-statement` refusal, as it cannot drop the index either. |
| `RENAME COLUMN` and `RENAME TO` | Without `--force`, refused with `not-native-safe-rewrite-required`, nothing executed: the catalog flip is instant, but every running application instance that still queries the old name breaks the moment it commits, and no safer sequence can be built from the statement alone because the dual-write and the read switch live in the application. The plan report, `suggest`, and the verdict carry the manual path as typed guidance — `expand-contract-column` for a column (add the new column, dual-write and backfill, switch reads, drop the old column as its own reviewed change) and `coordinated-table-rename` for a table (coordinate the rename with the deploy that adopts the new name, or keep the old name readable through a view until every instance has moved) — and `lint` reports the rename as an error. `--force SCHEMA.TABLE` runs the submitted rename as a blind bounded attempt under the usual budgets and size guard, for the operator who has coordinated the deploy; on a table above `--max-table-size` (default 1 GiB) the forced rename is refused as `not-native-safe-table-too-large` until that threshold is raised. |
| `ALTER INDEX ... RENAME TO` on an index that backs a primary-key, unique, or exclusion constraint | Refused with `not-native-safe-rewrite-required`, class `by-design`, guidance `coordinated-constraint-rename`, nothing executed: PostgreSQL renames the constraint with its index, and `ON CONFLICT ON CONSTRAINT` and error handling that name the old constraint break the moment it commits. `--force` does not apply to an index rename. A plain index rename runs. The refusal needs the catalog, so offline `lint` and `suggest` do not report it. |
| `ATTACH PARTITION` | Without `--force`, refused with `not-native-safe-rewrite-required`, nothing executed: `migrate` does not yet construct the validated `CHECK` that lets the attach skip its scan. The library entry `executor.AttachPartitionOnline` constructs every proof below and then attaches ([outcomes](schemabot-integration.md#outcomes-of-an-online-attach-partition)), but `migrate` does not route to it yet. Prove the attach unnecessary yourself, then run it directly: a validated `CHECK` for the bound on the new table, a validated `CHECK` excluding the bound on the parent's `DEFAULT` partition if it has one, each of the parent's indexes already on the new table, a unique one backing its constraint through `USING INDEX`, and each of the parent's foreign keys already on the new table, validated (`ADD ... NOT VALID`, then `VALIDATE`; one of the same definition under any name is reused). Without the second the attach scans the `DEFAULT` partition, without the third it builds the missing index, and without the fourth it creates the foreign key and checks every row against the referenced table, each under `ACCESS EXCLUSIVE` ([safe pattern](postgres-online-ddl-reference.md#safe-pattern-attach-a-partition-without-a-scan-or-an-index-build)). The new table must also carry the parent's `CHECK` constraints, under the same names and validated, and `NOT NULL` wherever the parent declares it, or the attach refuses it. `--force SCHEMA.TABLE` runs the blocking `ATTACH PARTITION` as submitted under bounded budgets, taking the blocking lock. |
| `DETACH PARTITION` beside a `DEFAULT` partition | PostgreSQL refuses `DETACH PARTITION ... CONCURRENTLY` on a table with a `DEFAULT` partition in every supported version, so `migrate` refuses both forms there with `unsupported-statement`, class `by-design`, from the catalog before anything executes, in `--dry-run` too. The only detach left is the plain one, which holds `ACCESS EXCLUSIVE` on the table and the partition while it runs: `--force SCHEMA.TABLE` (with `--allow-destructive`) runs it as submitted under bounded budgets. Detaching the `DEFAULT` partition first, itself a plain detach, makes the concurrent one possible. `suggest` cannot see the table and marks its `CONCURRENTLY` rewrite `no-default-partition`. Elsewhere a detach runs concurrently under `--allow-destructive`; an interrupted one fails with `partition-detach-interrupted` and is finished by running the same statement again, and while another partition of the table is detach-pending one fails with `partition-detach-pending` before anything runs, since PostgreSQL detaches one partition of a table at a time. `DETACH PARTITION ... FINALIZE` itself is refused with `unsupported-statement`, because the parser's reprint of it names a different partition: rerun the statement that started the detach. |
| Dropping what a replica identity index is built on | `REPLICA IDENTITY USING INDEX` outlives its index, so dropping the index, the primary key or unique constraint that owns it, or a column it covers leaves the table with no usable identity, and every `UPDATE` and `DELETE` on it fails while a publication publishes them. `REPLICA IDENTITY DEFAULT` keys on the primary key and fails the same way once it is dropped, so on a table a publication publishes updates or deletes for, the primary key counts as the identity index; on a table no publication publishes, it stays free to drop. The planner refuses such a drop with `replica-identity`, on the table and on what the drop reaches below it: a `DROP COLUMN` reaches partitions and inheritance children unless the statement says `ONLY`, and a `DROP CONSTRAINT` reaches partitions, whose indexes are attached under the parent's. The executor reads the identity again under the lock the drop takes, so an identity that moved onto the dropped object after planning still refuses the run before anything commits. `migrate --accept-blocking` makes the same check before a `DROP INDEX`. Point `REPLICA IDENTITY` at a unique index the drop leaves in place (`USING INDEX`), at a primary key it leaves in place (`DEFAULT`), or at the whole row (`FULL`, which logs every column of the old row) first, then re-plan. |
| Retyping or dropping a column a view reads | PostgreSQL refuses `ALTER COLUMN TYPE` and `DROP COLUMN` on a column a view or materialized view reads, even for a type change it would relabel in place. Without `ONLY`, a type change reaches the column on every partition and inheritance child too, and a drop reaches every partition and each inheritance child that does not declare the column and inherits it only from tables the drop also reaches; a child that declares the column or also inherits it from a table outside the drop keeps its copy, while one that inherits it along two paths from the dropped table loses it. The planner reads the views on every copy the change reaches from the catalog and refuses the change with `dependent-view`, naming each view in the plan and in the verdict's `dependent_views`, instead of letting the statement fail at the server. `DROP COLUMN … CASCADE`, which would drop the views with the column, is refused with `cascading-drop`. pg-sprite does not drop and recreate the views for you. The refusal names a materialized view by its kind, and its help gives the manual path the change takes: change the views so they no longer read the column before a drop, recreate them around an in-place type change in one transaction (a materialized view runs its query again to fill itself, while the transaction blocks the table), or point them at a new column for a type change that rewrites the table. The help also names the views that read those views, deepest first, to drop first and recreate last, and says to recreate the grants and materialized-view indexes a dropped view loses. |
| Retyping or dropping a column a policy reads | PostgreSQL refuses `ALTER COLUMN TYPE` (`cannot alter type of a column used in a policy definition`) and `DROP COLUMN` on a column a row-level security policy reads in its `USING` or `WITH CHECK` expression, even for a type change it would relabel in place, such as widening a `varchar`. The policy counts wherever it is defined: on the table, on a partition or inheritance child the change reaches (the same reach as for a view), or on another table whose policy reads the column through a subquery. The planner reads those policies from the catalog and refuses the change with `dependent-policy`, naming each as `"policy" ON "schema"."table"` in the plan and in the verdict's `dependent_policies`, instead of letting the statement fail at the server. pg-sprite does not drop and recreate the policies for you. The refusal's help gives the manual path: before a drop, change the policies so they no longer read the column; around an in-place type change, drop and recreate them in the same transaction, so no session sees the table without them; for a type change that rewrites the table, add a column of the new type, backfill it, and point the policies at it, since copy-and-swap rebuilds the policies before it retypes and meets the same refusal. A row-security file that retypes the column and keeps the policy's text gets this refusal, not a row security difference: PostgreSQL prints the same policy on the new type with a cast, such as `(owner_name)::text`, so the live policies are created again on the file's table definition in the rolled-back scratch transaction and compared as printed there. |
| Retyping or dropping a column a trigger, a generated column, or a partition key depends on | PostgreSQL refuses `ALTER COLUMN TYPE` and `DROP COLUMN` on a column that a trigger's `UPDATE OF` list or `WHEN` condition names (`cannot alter type of a column used in a trigger definition`) or that a generated column's expression reads (`cannot alter type of a column used by a generated column`), even for a type change it would relabel in place (PostgreSQL 14 instead drops the generated column along with a dropped column, without saying so), and never retypes or drops a partition key column (`42P16`). The planner reads these dependents from the catalog, with the same reach as for a view, and refuses the change with `dependent-trigger`, `dependent-generated-column`, or `partition-key`, naming the objects in the plan and in the verdict's `dependent_triggers`, `dependent_generated_columns`, or `partition_key_tables`. pg-sprite does not drop and recreate them for you. The refusal's help gives the manual path: for triggers, the same three paths as for policies; for generated columns, drop them first, knowing that adding a `STORED` one back rewrites the table; for a partition key, a new partitioned table with the new column definition that the rows move into. A trigger whose function body reads the column does not block the change, and is not refused. |
| Retyping or dropping a column a publication names | PostgreSQL refuses `ALTER COLUMN TYPE` and `DROP COLUMN` on a column that a publication's column list or row filter for the table names (`cannot alter type of a column used by a publication WHERE clause`, said for a column list too). The planner reads these publications from the catalog, with the same reach as for a view, and refuses the change with `dependent-publication`, naming them in the plan and in the verdict's `dependent_publications`. pg-sprite does not change a publication for you, since what a subscriber receives is the publication owner's decision. The refusal's help gives the manual path: remove the column from the publications with `ALTER PUBLICATION ... SET TABLE`, and for a type change add it back afterwards. A publication without a column list or row filter does not block the change. A publication that starts naming the column after planning, for a reviewed plan or a drop submitted with `--alter`, stops the run with `dropped-object-drift`, read under the table's lock, before anything is dropped. The error and the verdict's `detail` name the publication. |
| Adding a `NOT NULL` column with no default to a table that holds rows | PostgreSQL refuses it (SQLSTATE `23502`), because every existing row would hold `NULL` in the new column. The `NOT NULL` can come from the statement, the column's domain, or an inline `PRIMARY KEY`. The planner adds the column to a one-row temporary table to see whether PostgreSQL leaves it `NULL` or something fills it, such as its domain's `DEFAULT`, and only then reads whether the table holds rows, skipping foreign tables, whose rows PostgreSQL does not check, reading at most one row and never waiting for a lock, and refuses the change with `not-null-without-default` instead of letting it fail at the server under the table's exclusive lock. Give the column a constant default, or add it without `NOT NULL`, backfill it, and set `NOT NULL` afterwards. A read another session's lock blocks fails the plan with an error; retry once the lock is released. Rows a row-level security policy hides from the role do not count, so for such a role the server's refusal remains the backstop. |
| Dropping with `CASCADE` | `CASCADE` on `DROP COLUMN`, `DROP CONSTRAINT`, or `DROP INDEX` also drops whatever depends on the target: a view or policy that reads the column, or another table's foreign key on the constraint. Those objects are not in the statement, so the plan cannot show them and the table's lock does not cover them. The planner refuses every such drop with `cascading-drop`. Drop each dependent object as its own change, then resubmit without `CASCADE`; PostgreSQL then refuses the drop while anything still depends on the target. |
| `ADD COLUMN` on a hot standby, or by a role without `TEMPORARY` | Whether adding a column rewrites the table is the server's answer, read by adding the column to an empty temporary table. A server that accepts no writes, or a role whose `TEMPORARY` on the database was revoked, cannot create that table, so the plan fails with `ErrAddColumnProbeUnavailable` before anything runs. Plan against the primary, or grant `TEMPORARY` on the database to the engine's role. |
| Copy-and-swap | The route is in preview and closed by default: a run opens it with `--copy-and-swap` (`CopySwapOptions.Enabled` as a library caller), and without it a statement routed to the backend is refused `copy-and-swap-refused` with cause `copy-and-swap-not-enabled` before the route's preflight runs or anything is written (routing itself still reads the catalog), while natively executable statements are unaffected ([copy-and-swap.md](copy-and-swap.md#preview-the-route-is-closed-until-you-open-it)). The copy-and-swap backend carries a general `ALTER COLUMN TYPE` (with or without `USING`): the changed shape is built as a shadow table, filled in chunks while writes stream through a logical replication slot, verified, and swapped in under the source's name. The run needs `--free-disk` (the preflight refuses `copy-and-swap-disk-headroom` when the shadow and its indexes would not fit, or, for a live run, when they and the slot lag ceiling would not fit together; a resumed run is asked only for what is left to grow, the shadow already built and the WAL its slot already retains read from the server and subtracted, while a `--restart` run is checked as fresh) and either logical decoding (`wal_level = logical`, a free replication slot) or `--block-writes SCHEMA.TABLE`, which names the table whose writes it blocks until the swap; its preflight refuses table shapes it cannot run against — no primary key or usable replica identity ([primary-keys.md](primary-keys.md) covers choosing and adding one), unlogged, partitioned, `FORCE ROW LEVEL SECURITY`, foreign keys in either direction, triggers, dependent views, membership in a publication, or a subscription on the database — each as a typed `copy-and-swap-refused` cause ([refusal-classes.md](refusal-classes.md#copy-and-swap-refused-keyed-on-copyswaprefusalcause)). `--dry-run` reads one of those shapes from the catalog the same way: a partitioned parent, a partition, or a member of an inheritance tree ends the dry run in the run's own refusal verdict, cause `copy-and-swap-partitioned` (`copy-and-swap-unlogged` or `copy-and-swap-force-rls` instead when the table is also UNLOGGED or forces row security, which the preflight decides first), exit 2; the other shapes, the privileges, and the environment are read only when the change runs. The other rewrite-class operations — volatile-default `ADD COLUMN`, `ADD COLUMN` of a domain with a `CHECK` or `NOT NULL`, `GENERATED … STORED`, `SET TABLESPACE` — route to the backend but it does not carry them yet; they refuse `backend-unavailable`. `SET TABLESPACE` on a partitioned parent is the exception: the parent has no storage, so PostgreSQL only records the tablespace for partitions created later, under a brief `ACCESS EXCLUSIVE` on the parent alone, and the statement runs natively as metadata-only, moving no existing partition. pg-sprite never falls through to a blocking rewrite. A run that stops short of the swap keeps its hold on the source until it is resumed or abandoned — the write fence of a `--block-writes` run (every write is refused `55006`), or the replication slot of a live run, which pins WAL on the server — and the `failed` verdict's detail says which applies: a stop the next run clears (a lost connection, a cancelled run) resumes from the checkpoint row when the same statement is run again; a stop the data causes meets the same rows again, so it is not resumed: when the server rejects a row under the new type or a constraint (SQLSTATE class `22` or `23`) the run abandons itself — drops the shadow, releases the fence or slot, deletes the checkpoint row — and the verdict is `failed` with `code: data-fault`, so correct the data or the statement and run it again from the beginning; when the shadow and source diverge at verification (or the abandon itself failed), the row and the hold stay and the run has to be started over: correct the data or the statement, then run it with `--restart SCHEMA.TABLE` (`CopySwapOptions.Restart` as a library caller), which drops the shadow, releases the fence or slot, deletes the checkpoint row, and runs the change fresh under the run's own lock ([stopping, resuming, and starting over](schemabot-integration.md#stopping-resuming-and-starting-over)). While a stopped run's checkpoint row stands, its own statement resumes it through copy-and-swap even where the shape it may already have swapped in would route the statement natively, and every other statement on the table is refused `copy-and-swap-refused` with cause `copy-and-swap-run-stopped` before anything runs, as is a desired-state run whose plan for the table is empty, a reviewed plan's index drop, and a row security file's change: run the stopped statement again to finish it (before the swap, a statement that routes to copy-and-swap may start over under `--restart` instead). `--dry-run`, imperative or desired-state, reads the row too and ends in the same refusal. `ALTER TYPE ... ADD VALUE` is the one change that still runs, since it locks no table and an enum label is not part of a table's shape, so the stopped run resumes after it. |
| `ALTER COLUMN TYPE ... USING <expr>` the copy cannot reproduce | The copy-and-swap route (above) runs the retype, but the shadow builder admits a `USING` expression only when it can evaluate it again, identically, in the chunk copy, the verifier's recopy, and every change the catch-up flushes. Three rules, each refused as `shadow-statement-conversion` before any shadow is committed: the expression must be **immutable** by the server's own classification (no `now()`, `random()`, `current_setting()`, session-dependent casts such as `text` to `timestamptz`, or functions declared `STABLE` or `VOLATILE`; checked by trying it as a stored generated column's expression on the empty shadow inside the build's transaction, then rolling that attempt back), it must **name only the column it retypes**, bare and unqualified (no neighbouring column, no `t.col`, no whole-row `t.*`), and it must not retype the **primary key**, whose values every chunk range, watermark, and resume clear are expressed in. The expression is also refused when the deparser cannot prove it rendered the text faithfully. Rewrite the expression in terms of the retyped column alone and of `IMMUTABLE` functions, or retype without `USING` so the server's assignment cast converts the value; the refusal names the column, the expression, and that rewrite. The spellings most often refused, and what to write instead, are in [`USING` expressions the copy reproduces](#using-expressions-the-copy-reproduces) below. |
| A schema change to the source table while a copy-and-swap runs | Unsupported: logical decoding does not stream DDL, and the copy does not lock it out — a chunk holds `ACCESS SHARE` on the source only for its own transaction, so `ALTER TABLE` on the source completes between chunks. The copy selects the source by column name, so what happens depends on whether every copied name still resolves. A copied column renamed or dropped stops the copy at its next chunk with the server's `undefined_column` error (SQLSTATE `42703`), which is not a typed refusal; that chunk stays in flight and nothing from it reaches the shadow. A change that leaves every copied name resolving to a column of a compatible type — two columns swapping names, a column renamed and re-added under the old name, a widened type — is not detected by the copy, which completes, and after a swap or a re-add the rows copied since hold another column's values or the new column's default. Once the replication stream has decoded a change to the table, a later relation description that differs stops it with `ErrSourceShapeChanged`. None of these reaches the swap: the verifier compares source and shadow rows by column name, and the cutover gate re-fingerprints the source and refuses any changed column as `cutover-schema-drift` ([refusal-classes.md](refusal-classes.md#shadow-operation-refusals-keyed-on-refusalcause)), after which the shadow is dropped and the change re-planned. |
| A concurrent index build whose name is occupied by an invalid index, or whose table carries quarantined debris | The build refuses before running and never drops the occupant: an invalid entry is either abandoned debris or someone's build still in progress, and a drop by name cannot tell them apart. The refusal is typed by proof (`invalid-index-abandoned`, `invalid-index-build-in-flight`, `invalid-index-other-table`, `invalid-index-not-droppable`, `invalid-index-builder-unobservable`), and a table carrying an entry a previous recovery quarantined (`pgsprite_abandoned_<oid>`) but did not drop is refused the same way, so debris never goes quiet. The proven removal — `executor.RebuildAbandonedIndex`, or `executor.DropAbandonedIndex` to remove the leftover without running the build; both library-only today, no CLI verb — takes a bounded `SHARE UPDATE EXCLUSIVE` lock on the table (which any running concurrent index command holds), re-verifies the entry by OID, renames it to an identity-derived name and drops that, all within one shared budget; it refuses a visible in-flight build, another table's entry, or an entry the server will not drop concurrently (a partitioned table's index, an index partition, a constraint's index), and reports a lock budget rather than wait behind a build it cannot see. From the CLI, the [runbook](invalid-index-recovery.md) applies. |
| A copy-and-swap statement that drops a column and adds one of the same name | Like any drop, it runs only under `--allow-destructive`; without it the statement is refused with `destructive-change` and the `alter-column-type-in-place` guidance before the shadow build starts. Under the acknowledgement, the re-added column is a new column: every row holds its default (or NULL), as under a direct `ALTER TABLE`, and the dropped column's values are not copied into it ([copy-and-swap D1](copy-and-swap-design.md#d1--no-durable-scratch-database)). Three such re-adds have no default to take or are the key the copy is driven by, and the shadow build refuses them with `shadow-statement-readd` inside its own transaction, before any shadow, fence, or checkpoint row exists: re-adding the primary key column, re-adding a source identity column, and re-adding a column that refuses NULL (by its own `NOT NULL` or its domain's) with no default of its own or on its type. The remedy depends on which: a primary key is refused whatever the new column declares, so a default does not help — change the key in place with `ALTER COLUMN TYPE`; a source identity column is refused whatever the new column declares too — drop it in one schema change and add the new column in the next; any other column runs once the re-added column has a default (its own, or its domain's). A nullable, defaulted, or generated re-add builds and runs. A `NOT NULL` column added beside the other changes rather than re-added, or the key dropped or replaced under a new name, is refused by the next check, `shadow-statement-new-column` (next row). A re-add declared as an identity or `serial` is refused in the same transaction with `shadow-statement-new-sequence` (row after next). The refusal covers only what the catalog states: a new or re-added column whose fill a constraint rejects — a `CHECK` that rejects the column's default or NULL, or a `UNIQUE` or exclusion constraint on a column whose constant default every copied row would repeat — still builds and stops at the first chunk, failing closed; that stop is the server's class `23` error, a data fault, so the run abandons itself and the verdict is `failed` with `code: data-fault`. A run checkpointed by an earlier build for a drop-and-re-add statement no longer resumes (`resume-row-mismatch`, because the copy list it recorded names the re-added column); abandon it and run again rather than retrying the resume. |
| A copy-and-swap statement that adds a column the copy cannot fill, or leaves the table without its key | The copy list names only the source columns the shadow kept as the same column ([ST-11](invariants.md#st-11--the-shadow-takes-a-columns-values-only-from-the-same-source-column)); every other shadow column is a new column that takes its own default (or NULL) on every copied row, as under a direct `ALTER TABLE`. Two shapes have nothing to take, and the shadow build refuses them with `shadow-statement-new-column` inside its own transaction, after the statement has run on the empty shadow and both relations' column positions have been read, so no shadow, fence, or checkpoint row exists: a new column that refuses NULL (by its own `NOT NULL` or its domain's, including a domain its type is built on) with no default of its own or on its type, no generation expression, and no identity — `ALTER COLUMN qty TYPE bigint, ADD COLUMN region text NOT NULL` — and the source's primary key missing from the shadow's kept columns, dropped outright or replaced by a key under a new name — `DROP COLUMN id, ADD COLUMN new_id bigint PRIMARY KEY, ALTER COLUMN qty TYPE bigint`. Without the refusal both would build and commit a shadow: the first then stops at the first chunk with the server's `not_null_violation`, a data fault that abandons the run and reports `code: data-fault` for a statement no data could have satisfied; the second stops at the applier's own check that the copy list names the primary key, as an `invariant-violation` failure that leaves the shadow, the checkpoint row, and the replication slot behind, pinning WAL until the run is restarted. From the CLI these shapes reach the build only beside an operation that routes to copy-and-swap, such as the retype above: on its own, `ADD COLUMN … NOT NULL` without a default is routed native and the server rejects it on a non-empty table, `ADD COLUMN` of a `NOT NULL` domain is `backend-unavailable`, and a dropped key is native. Beside a retype, every natively-routed operation rides along into the gated statement, so the build-time refusal is what stands between the operator and the first-chunk fault; it is also the library path's guard (`schemachange.Runner`, `BuildShadow`). A missing key is refused whatever the new key declares, because the key column must stay for the copy: to retype the key, change it in place with `ALTER COLUMN TYPE`; to drop it, run the drop as its own schema change (a drop alone is routed native). For a new column, give it a default (its own, or its domain's), or add it nullable or with a default in its own schema change, fill it, then `SET NOT NULL`; a nullable, defaulted, or generated new column builds and runs. A new column declared as an identity or `serial` is fillable and is refused by the next check, `shadow-statement-new-sequence` (next row). |
| A copy-and-swap statement that gives the table a new identity or `serial` column | The swap carries only the source's sequences to the live table — each re-owned by the shadow column that kept its source column's name — so a sequence the gated statement mints on the shadow (`ADD COLUMN … GENERATED … AS IDENTITY`, `ADD COLUMN … serial`, `ALTER COLUMN … ADD GENERATED … AS IDENTITY` on a kept column, or a dropped column re-added as one) has no source counterpart to carry. The shadow build refuses such a statement with `shadow-statement-new-sequence` inside its own transaction, after the statement has run on the empty shadow and the shadow's columns and sequence-ownership edges have been read, so no shadow, fence, or checkpoint row exists; the source's own serial and identity columns are not new sequences and pass. From the CLI these statements are routed before the build reaches them — a new identity or `serial` column is a volatile-default `ADD COLUMN`, which the copy-and-swap backend does not carry yet (`backend-unavailable`), and `ADD GENERATED` on an existing column is `unsupported-operation` — so the build-time refusal is the library path's guard (`schemachange.Runner`, `BuildShadow`) and the engine's own defence should a route later admit them. Declare the column plain in this schema change. pg-sprite does not run the follow-up: add the identity (after filling the column and setting it `NOT NULL`) with a direct `ALTER COLUMN … ADD GENERATED … AS IDENTITY`, or attach a sequence with a direct `CREATE SEQUENCE … OWNED BY` and `SET DEFAULT nextval(…)`. |

## Boundaries at a glance

The README's short list points here. Each entry is a boundary where an operation
fails closed with a typed refusal, never a silently wrong or incomplete result;
the table above and [capabilities.md](capabilities.md) give the mechanics and the
per-operation status.

- **Copy-and-swap** (genuine table rewrites) is in preview: it has not yet
  been exercised under production-like load, so the route stays closed until
  a run opens it with `--copy-and-swap` (`CopySwapOptions.Enabled` as a
  library caller); without it a statement routed there is refused before
  anything runs, and every native change is unaffected
  ([running a copy-and-swap](copy-and-swap.md#preview-the-route-is-closed-until-you-open-it)).
  Open, it carries a general
  `ALTER COLUMN TYPE` today; the other rewrite-class operations (volatile-default
  `ADD COLUMN`, `GENERATED … STORED`, `SET TABLESPACE` of a table with storage) refuse rather than fall
  through to a blocking rewrite, and the route's preflight refuses table shapes
  and environments it cannot run against. The shadow build also refuses a
  statement the copy cannot carry: a `USING` expression it cannot reproduce,
  a dropped-and-re-added or new column it cannot fill, a key it would not
  keep, or a new identity or `serial` column whose sequence the swap cannot
  carry. A run on a pool smaller than its copy workers plus two is refused
  before it creates anything, from every entry point
  ([the pool floor](#the-copy-and-swap-pool-floor)).
- **Connection poolers**: point pg-sprite directly at the primary; the
  application keeps whatever pooling it uses. pg-sprite's own connection
  through a pooler is unsupported, except Supabase's Supavisor session
  endpoint for native schema changes. Startup checks usually refuse a
  transaction-mode pooler, but passing them does not make it supported
  ([connections and poolers](#connections-and-poolers)).
- **Row security** is included in exports when present, with reviewable before/after differences. The
  [atomic executor](atomic-row-security.md) applies RLS-only changes to existing tables,
  and creates a missing table together with its row security in one transaction, through
  `migrate --desired` or the Go API. Only the Go API supports binding execution to an ordered
  SQL review, and only for an existing table. A table change in a file whose row security already
  matches runs as an ordinary desired run; a change to both remains unsupported. See the workflow and roadmap in
  [declarative-row-security.md](declarative-row-security.md).
- **Foreign keys** a desired file adds run online, as `NOT VALID` then
  `VALIDATE`, or partition by partition on a partitioned table before
  PostgreSQL 18, and a new table is created with its foreign keys. A foreign
  key the file no longer declares is dropped, as a destructive change that
  needs `--allow-destructive`. A key the file declares under a new name is
  added and validated before the old one is dropped. If rows break the new
  key, the validation fails and both keys stay: the old one valid, the new one
  `NOT VALID` but checking every new write. Fix the rows and the next plan
  validates the new key and drops the old one; or take the new key out of the
  file and the next plan drops it. A key changed under the same name is dropped
  and re-added `NOT VALID` in one statement, so every write stays checked by
  one key or the other, and then validated; if rows break the new key, it stays
  `NOT VALID`, checking every new write, until the rows are fixed and the next
  plan validates it. On a partitioned table, or in a plan that also drops or
  retypes a column, the drop would come before the add and leave writes
  checked against no key, so it is refused. So is the drop of a key a file
  cannot declare: one into another
  schema, or one from a table to itself whose referenced columns are unique
  only through a standalone unique index. Both refusals use
  `declarative-foreign-key`. Export refuses foreign keys unless the caller
  opts in with `RenderOptions.ForeignKeys`.
- **Changed stored generated expressions** are planned but not executed:
  `diff` shows one `SET EXPRESSION` statement (PostgreSQL 17+) refused with
  `unsupported-statement`, since it recomputes every row under an exclusive
  lock. Virtual generated columns (PostgreSQL 18+) are not modeled: export
  refuses them and a desired file that redeclares one fails the diff.
- **Identity and serial sequence declarations** are modeled but not
  converged: an identity's declared options export and compare, and a
  difference is a typed `diff` refusal; change the declaration with owner
  tooling, then state it in the file. A serial cannot state one, so export
  refuses a serial whose sequence was declared otherwise.
- **Partitioned tables** support in-place statement changes, and a `CREATE INDEX`
  on a partitioned table runs partition by partition, resuming when the same
  statement is run again; a unique one that lacks a partition key column is
  refused, as PostgreSQL rejects it. `migrate --alter` runs a named
  `ADD PRIMARY KEY` or `ADD UNIQUE` on a partitioned table the same way, one
  partition at a time, and so does `migrate --desired` for a key a desired file
  adds; a key on a tree with sub-partitioned partitions is refused. Only a partitioned parent can be expressed in or
  exported to a desired file — partitions and their bounds stay owned outside
  it — and `migrate` refuses `ATTACH PARTITION` unless `--force` names the table.
  `DETACH PARTITION` runs as `DETACH PARTITION ... CONCURRENTLY` under
  `--allow-destructive`, except beside a `DEFAULT` partition, where PostgreSQL
  allows only the blocking form and `--force` has to name the table
  (see the table above). A reviewed
  `migrate --desired` column or constraint drop on a partitioned parent removes it
  from every partition; the column drop is refused, dropping nothing, when the column
  is in a partition key at any level or a partition carries an index, constraint, or
  statistics object of its own on it. A reviewed `NOT NULL` drop on a partitioned
  parent is refused, and so is a reviewed column, constraint, or `NOT NULL` drop on
  a table with inheritance children.
- **Index maintenance** is not driven by `migrate --alter`: it refuses `DROP INDEX`
  and `REINDEX` (plain or `CONCURRENTLY`); see the `--accept-blocking` entry below.
  `migrate --desired` does run a planned index drop, as `DROP INDEX CONCURRENTLY`
  under `--expect-fingerprint` and `--allow-destructive`.
  An index of a partitioned table has no concurrent drop at all: drop it with
  the plain `DROP INDEX` under `--accept-blocking SCHEMA.TABLE` and
  `--allow-destructive SCHEMA.TABLE`, naming the parent, which locks the parent and
  every partition while it runs
  ([example](lock-budgeted-passthrough.md#dropping-an-index-of-a-partitioned-table)),
  through `migrate --alter` or from the reviewed plan through `migrate --desired`
  with `--expect-fingerprint`.
  A partition's index attached under the parent's is refused in either form; drop
  the parent's index instead.
- **Renames are refused, not run**: `RENAME COLUMN` and `RENAME TO` are
  instant in the catalog but break every running application instance that
  still uses the old name, and no safer sequence can be built from the
  statement alone, so `migrate` refuses them as `rewrite-required` with the
  expand-and-contract (column) or coordinated-deploy (table) path as typed
  guidance; `--force SCHEMA.TABLE` runs the submitted rename for the operator
  who has coordinated the deploy. `ALTER INDEX ... RENAME TO` runs for a plain
  index, but is refused, with no `--force` override, for an index that backs a
  primary-key, unique, or exclusion constraint, since it renames the constraint.
- **Unlogged tables and explicit column collations** are outside the
  declarative model: converging either is a table (or column) rewrite, so
  export and diff refuse rather than plan one.
- **Two key constraints declared the same way** (`PRIMARY KEY`, `UNIQUE`,
  or `EXCLUDE` on the same columns) cannot be declared in a desired file,
  because one `CREATE TABLE` keeps only one of them. Export refuses such a
  table, and a desired file that declares both fails its build instead of
  planning the second one's live copy away.
- **A key whose storage parameter cannot be rendered is refused** —
  `ADD PRIMARY KEY` / `ADD UNIQUE` runs as a concurrent index build plus
  `USING INDEX`, carrying the key's `WITH (...)` parameters; a value that
  is not a plain word, number, or string, contains a backslash, or a
  namespaced parameter name refuses with `rewrite-required` and the steps
  to build the index by hand, then attach it.
- **Dropping what a replica identity index is built on is refused** — the
  index, the constraint that owns it, or a column it covers; move
  `REPLICA IDENTITY` first, then re-plan.
- **Retyping or dropping a column a view reads is refused** — PostgreSQL would
  refuse it anyway; the plan names the views and the manual path for them.
- **Retyping or dropping a column a row-level security policy reads is refused**
  — PostgreSQL would refuse it anyway; the plan names the policies to drop and
  recreate around the change.
- **Retyping or dropping a column a trigger, a generated column, or a partition
  key depends on is refused** — PostgreSQL would refuse it anyway; the plan names
  the triggers, generated columns, or partitioned tables in the way.
- **Retyping or dropping a column a publication's column list or row filter
  names is refused** — PostgreSQL would refuse it anyway; the plan names the
  publications to take the column out of first.
- **Adding a `NOT NULL` column with no default to a table with rows is refused**
  — PostgreSQL would refuse it anyway, after taking the table's exclusive lock;
  the plan suggests a constant default or a backfill first.
- **Destructive statements need a typed acknowledgement** — `migrate --alter`
  refuses a statement that drops a column, a constraint, or a `NOT NULL` with
  `destructive-change` (exit 2) on every route and in `--dry-run`, unless
  `--allow-destructive SCHEMA.TABLE` names the table; the acknowledged run is
  audited and its verdict carries `allowed_destructive: true`. A drop that
  adds the same column back gets the guidance to change its type in place,
  which keeps its values. A `DROP INDEX` run under `--accept-blocking` needs
  `--allow-destructive` too: accepting the lock is not accepting the loss,
  and the refusal lists the checks (`idx_scan` on every replica, foreign
  keys, uniqueness) that catch an index the application still uses, with
  the connected server's own scan count for the index in `index_usage`.
- **Destructive desired-state plans are refused as a whole unless you pin them** —
  `migrate --desired` creates missing tables and converges supported changes, but never
  infers permission to discard live structure. Review the plan with `diff --desired`,
  then run it with `--expect-fingerprint` (the `sha256:...` value `diff` prints) and
  `--allow-destructive SCHEMA.TABLE`: the run executes only that plan, and each
  destructive statement is audited and marked `allowed_destructive: true`. A dropped
  index runs as `DROP INDEX CONCURRENTLY`. Row security policies are separate: a
  policy drop in a desired file is already atomic and needs no acknowledgement. A new primary key or unique constraint over a live
  unique index of its name is not destructive: it takes the index over with
  `ADD CONSTRAINT ... USING INDEX`, and refuses with `adopted-index-drift` if the
  index changed after planning. Nor is a live check constraint left `NOT VALID`
  with the desired definition: it plans as one online `VALIDATE CONSTRAINT`, and
  refuses with `validated-constraint-drift` if the constraint changed after planning.
  A change between `timestamp` and `timestamptz` planned to relabel in a UTC
  session refuses with `time-zone-drift` if the session that runs it is no
  longer in UTC; plan again.
- **Invalid-index recovery has no CLI verb yet** — a failed concurrent index
  build's leftover is reported with a typed state (and named by `diff` as a
  typed plan advisory), and the proven removal
  (`executor.RebuildAbandonedIndex`, or `executor.DropAbandonedIndex` when
  the caller must not rebuild) is library-only; from the CLI the
  [runbook](invalid-index-recovery.md) applies.
- **The accepted-blocking passthrough covers index maintenance only** —
  `migrate --accept-blocking SCHEMA.TABLE` runs an otherwise-refused plain
  `DROP INDEX` (not `CASCADE`), `REINDEX INDEX`, or `REINDEX TABLE`
  deliberately under the engine's bounded lock and statement budgets, with
  the verdict marked `executed-without-online-safety` (exit 3). A `DROP INDEX`
  also needs `--allow-destructive` naming the same table. Every other
  refusal — including a forced blocking index build on a partitioned parent —
  still exits 2. Design:
  [docs/lock-budgeted-passthrough.md](lock-budgeted-passthrough.md).
- **Non-table objects** — views, standalone sequences, enums, domains,
  extensions, functions, triggers — are outside the declarative model,
  which covers one ordinary table (or one partitioned parent) plus its
  indexes per file. A table may
  use them: the file names an object outside the table's schema and
  `public` qualified, or names it bare when `--extension-schema` lists
  the schema it lives in. The object's own definition is never managed,
  with one exception: a desired file can hold one `CREATE TYPE ... AS ENUM`
  instead of a table, and `diff` and `migrate --desired` add the labels the
  live type lacks with `ALTER TYPE ... ADD VALUE`, which locks only the
  type. The type must already exist, and a label is never removed, renamed,
  or moved; `migrate` also adds a value imperatively.
- **Dropping a table** is never planned or executed. pg-sprite converges
  one declared table at a time, so a live table with no desired file is
  the whole-schema owner's to enumerate and resolve — see
  [Deliberately operator-owned](capabilities.md#deliberately-operator-owned).
- **Greenfield create shapes** the create path cannot run — `PARTITION OF`,
  `INHERITS`, `LIKE`, `OF`, `IF NOT EXISTS`, or a relation name the desired
  set claims twice — refuse at plan time, and the same rules re-check at
  apply.
- **A desired file that names a live parent** with `PARTITION OF` or
  `INHERITS` refuses before planning builds anything, since the scratch
  build would lock that parent.

## `USING` expressions the copy reproduces

The bar is the server's own classification, read by trying the expression as a stored
generated column's expression: `IMMUTABLE`, not `STABLE`. `STABLE` promises one answer
within a statement, not across the hours a copy takes or the sessions the catch-up opens.
Many conversions people write for a retype are refused not because they read the clock
but because the builtin behind them is `STABLE` — any cast whose text form depends on
`DateStyle`, `TimeZone`, or the enum's catalog entry is. The refusal arrives at the shadow
build, inside the run, after the plan has been reviewed: the plan cannot read volatility
off the statement's text, so a plan that reads clean can still stop at this gate.

| Refused spelling | Why the server refuses it | What to write |
| --- | --- | --- |
| `enum_col::text` | `enum_out` is `STABLE`: the label comes from the catalog | Retype to `text` without `USING`; the assignment cast converts the label |
| `date_col::text`, `timestamp_col::text`, `timestamptz_col::text` | `date_out` and friends are `STABLE`: the text follows `DateStyle` (and `TimeZone`) | An `IMMUTABLE` wrapper of your own that fixes the format, e.g. `to_char(d, 'YYYY-MM-DD')` inside a function declared `IMMUTABLE` — `to_char` itself is `STABLE` |
| `text_col::date`, `text_col::timestamp`, `text_col::timestamptz` | The input functions are `STABLE`: parsing follows `DateStyle` and `TimeZone` | A wrapper declared `IMMUTABLE` that parses one fixed format |
| `to_char(...)`, `to_date(...)`, `to_timestamp(text, text)` | Declared `STABLE`: they read `lc_time` and the session's style settings (`to_timestamp(double precision)` is `IMMUTABLE` and admitted) | A wrapper declared `IMMUTABLE` around the one format you use |
| `convert_to(text_col, 'UTF8')` | Declared `STABLE`: the result depends on the database encoding | A wrapper declared `IMMUTABLE` around the one encoding you use; `decode(text_col, 'escape')` is **not** a general substitute — it interprets backslash sequences, so it equals `convert_to` only for text that contains none |
| `now()::text`, `random()`, `current_setting(...)`, `nextval(...)`, a subquery | `VOLATILE`, or not an expression a generated column may hold | No rewrite reproduces these; the value is not a function of the source row |

A wrapper function is your assertion, not the server's: declaring it `IMMUTABLE` is what
admits it, and the server never checks the body. It must exist, in the source schema or
`public`, before the shadow build, since the expression resolves on that path in the build,
the copy, the recopy, and every flush ([CO-9](invariants.md#co-9--decision-reads-resolve-to-the-real-catalog)).
The build records a fingerprint of what the expression's names resolved to — the functions,
operators, types, and collations by name across that path, with each function's body,
strictness, `SET` settings, and argument defaults, and each collation's locale — and the
copy, the verifier, the catch-up, and the swap's final drain recompute it inside each of their
transactions, and once more after each write and before its commit. A function or operator
created, replaced, or dropped on that path after the build refuses the run as
`copy-conversion-drift`, and a run resumed over such a change is refused the same way until
the change is undone. Every one of those write transactions runs `READ COMMITTED`, whatever
`default_transaction_isolation` the server or role sets, so a write that resolved through the
change is rolled back by the second check. One case gets past both checks: a change made and
undone again between them. The verifier's comparison against the source is what catches the
rows it reached, except in the swap's final drain, which no comparison follows. Make the change
before the build, or abandon the run with `--restart` and build again over the new catalog.
The fingerprint covers only the names the expression spells: the functions a wrapper calls in
turn, and the function behind a cast the expression performs (`price::cents` through
`CREATE CAST`), are not under a spelled name and are not pinned. Keeping those still for the
length of the run is the wrapper author's responsibility.

Two casts the server does call immutable still have more than one text rendering: a
`float4` or `float8` to `text` follows `extra_float_digits`, and a `bytea` to `text`
follows `bytea_output`. The copy, the verifier, the catch-up, and the swap's final drain
each pin both settings (`3` and `hex`) in their own transactions, so such a conversion lands
the same text from all of them whatever the database or role is configured with.

## Connections and poolers

pg-sprite keeps state on each connection's PostgreSQL session: the execution bounds
(`lock_timeout`, `statement_timeout`) every statement runs under, and the per-table
advisory lock that keeps a second run off the same table. Each of its connections must
therefore stay on one session for its whole life. This is **session affinity**: every
statement sent on a connection runs on the same PostgreSQL backend, so a setting or lock
taken by one statement is still there for the next.

A direct connection always has it. A transaction-mode or statement-mode pooler does not:
it may hand the connection's next transaction to a different backend, one another client
may have just used, so pg-sprite's timeouts could silently vanish and two runs could both
believe they hold the same table lock ([session-affinity.md](session-affinity.md) explains
what depends on it). pg-sprite checks rather than assumes. When it opens
its pool it reads back the timeouts it set, and on the pool and again on the table lock's
own connection it takes a throwaway advisory lock, then confirms from a second connection
that the first still holds it and that the second cannot take it. A connection that drops
the timeouts is refused with `ErrSessionSettingsDiscarded`, and one that fails the lock
check with `ErrNoSessionAffinity`, before any schema change runs.

These checks guard against session loss they can observe; they cannot prove its absence.
An idle transaction-mode pooler with spare backends can keep a connection on one backend
for the length of the checks and move it later, so a clean start does not make a pooler
path safe. Connect directly to the primary.

This constrains only pg-sprite's own connection. The application keeps whatever pooling
it uses — a client-side pool, or a server-side pooler in session, transaction, or
statement mode — and copy-and-swap reads the application's writes from the WAL through
logical decoding, whichever pooler carried them.

| pg-sprite connects through | Support |
| --- | --- |
| A direct connection to the primary | Supported, and the recommended deployment. Every schema change path, copy-and-swap included, is tested this way. |
| Supabase's Supavisor session endpoint | Supported for the native schema changes listed in [supabase.md](supabase.md#what-works-today). Copy-and-swap through it is unsupported. |
| PgBouncer, or any other server-side pooler, in session mode | Unsupported. Connect directly to the primary. |
| Any pooler in transaction mode | Unsupported. Connect directly to the primary. The startup checks usually refuse it before any work runs, with `ErrSessionSettingsDiscarded` when the pooler drops the timeouts or `ErrNoSessionAffinity` when it moves the connection; the tests pin `ErrNoSessionAffinity` for PgBouncer and Supavisor in transaction mode. A pooler that passes the checks is still unsupported. |
| Any pooler in statement mode | Unsupported. Connect directly to the primary. Opening the pool refuses it with `ErrNoSessionAffinity`: the pooler rejects the check's transaction, which the tests pin for PgBouncer in statement mode. |

The application's pooler and pg-sprite share the server's `max_connections`, which has
to cover the application's backends plus pg-sprite's pool, its dedicated sessions, and,
for copy-and-swap, its replication connections.

### The copy-and-swap pool floor

A copy-and-swap run needs one pool connection per copy worker and two beside them, one
for the catch-up's flushes and one for checkpoint saves and progress reads: six with the
default four workers (`schemachange.MinPoolConns`). A pool of only the workers would leave
the flushes waiting behind the copy while the slot's lag grows, so a smaller pool is
refused with `executor.ErrPoolTooSmall` (`code: pool-too-small` on a verdict) before the
run takes the table lock or creates anything. The refusal is the same from every entry
point: `migrate`, the library's `migrate.Run` and `migrate.RunDesired`, and
`schemachange.Runner.Run` called directly. It also applies to resuming or restarting a
stopped run, which keeps its slot or write fence and its checkpoint row until the pool is
raised; a stopped live run's slot retains WAL on the source meanwhile. Raise the pool
(`pool_max_conns` on the URL) to at least the floor; the CLI's pool holds at least six
unless the URL sets `pool_max_conns`.

## Declarative model boundaries

The declarative front door (desired-state files, `diff`, and schema export)
models **one ordinary table plus its indexes** (or one partitioned parent with its
partition key and indexes, or one enum type, whose labels `diff` and
`migrate --desired` converge; export does not write one). These are the boundaries of
that model today. Wherever an operation meets a boundary, it fails closed
with a typed refusal — never a silently wrong or incomplete result:

| Not modeled | Current behavior |
| --- | --- |
| Row-level security (RLS) settings and policies | `pull` exports settings, policies, roles, and policy comments; `diff` verifies unchanged definitions and shows review-only RLS deltas before refusing changes. The [atomic executor](atomic-row-security.md), through the Go API or `migrate --desired`, supports RLS-only changes to existing supported tables, and creates a missing table together with its row security in one transaction. For an existing table, Go callers can preview and bind execution to the ordered generated SQL; this does not bind every earlier catalog value. Creating a table has a reviewed variant too, which binds the ordered table, index, and row-security SQL; the caller passes the same owner to the preview and the run, since the owner is not part of that SQL. A policy may read another table it names schema-qualified. Unqualified, self-referencing, `pg_catalog`, or row-locking policy relations, policies on an existing table that read a table whose policies read it back, and a change to both the table and its row security remain refused. A table change whose row security already matches the file runs as an ordinary desired run and leaves the policies unchanged. Tables without RLS get no extra SQL; table-only desired files leave access control separately managed. See the [RLS workflow and roadmap](declarative-row-security.md). |
| Foreign keys in a desired file | Added, dropped, and changed keys run. A desired file may declare a foreign key whose referenced table is unqualified and exists in the target schema, or is the table itself; a schema-qualified reference is refused at parse (`ErrQualifiedName`), a referenced table that does not exist fails the plan (`ErrReferencedTableNotFound`), and so does one the planning role cannot `SELECT` from (`ErrReferencedTableNotReadable`) or, for a key the plan adds, lacks `REFERENCES` on the referenced columns through a table or column grant (`ErrReferencedTableNotReferenceable`). A matching key plans no change. An added key runs online: `ADD ... NOT VALID`, then `VALIDATE CONSTRAINT` while writes keep flowing; a row that breaks it fails the validation and leaves the key `NOT VALID` but enforced for new writes. A new table is created with its keys. A live key the file leaves out plans as `drop-foreign-key`, a destructive change that needs `--allow-destructive`; the drop takes `ACCESS EXCLUSIVE` on both tables under the brief lock budget. A live key into another schema, or a key from a table to itself whose referenced columns are unique only through a standalone unique index, cannot be declared, so its drop is refused with `declarative-foreign-key`; remove it with `migrate --alter`. A key changed under the same name is replaced by one destructive `ALTER TABLE` that drops it and adds the new definition `NOT VALID`, so every write stays checked by one key or the other, and then validated; a validation that fails leaves the new key `NOT VALID`, checking every new write. On a partitioned table the old key would be dropped before the new one could take the name, leaving writes checked against no key in between, so its drop is refused with `declarative-foreign-key`; declare the changed key under a new name, and the plan adds and validates it before it drops the old one, so a validation that fails leaves the old key standing. The same drop is refused in a plan that adds a foreign key and also retypes a column, or drops one beside an added column that may rewrite the table, since that plan keeps its drops first. Incoming foreign keys are invisible to a single-table diff, export refuses a table that owns or is referenced by foreign keys unless the caller opts in with `RenderOptions.ForeignKeys`, which still refuses one into another schema, one from a table to itself whose referenced columns have no primary key or `UNIQUE` constraint, and one on a table rendered with row security; desired row-security files refuse foreign keys. |
| Partitions and partition topology | A partitioned parent is modeled with its partition key: `pull` exports it as `CREATE TABLE ... PARTITION BY` with its indexes as plain `CREATE INDEX` statements on the parent, and `diff` of that file against the same parent plans no changes. Partitions, their bounds, and the parent/partition topology are not modeled and stay owned outside the desired file: `pull` skips partitions, and export refuses a partition (`ErrUnrenderablePartition`), a parent whose index, or the index behind its primary key, unique, or exclusion constraint, is not attached on every partition (`ErrUnrenderableUnattachedIndex`), and a parent with row security (`ErrUnrenderablePartitionedRowSecurity`). The statement front door supports in-place changes on parents and partitions (see the partitioned-parent rows above). A partitioning mismatch between live and desired is a typed refusal (`capability-boundary`, exit 2), never a zero diff. A desired file whose `CREATE TABLE` is `PARTITION OF` a parent is refused before planning runs anything (`ErrDesiredPartitionOf`), because building it would attach to the live parent under `ACCESS EXCLUSIVE`. A desired file that declares several partitions, or a parent with its partitions, is refused at parse (`ErrDesiredPartitions`). `diff` and `migrate --desired` report both as an `unsupported-statement` refusal with the `capability-boundary` class and exit 2. |
| Classic table inheritance (`INHERITS`) | Both parents and children are refused during export. The model records classic inheritance edges in both directions only to fail closed: rendering a child would flatten inherited columns and rendering a parent would omit its children. Declarative partitions share `pg_inherits` but remain classified by `relispartition` and use the partition refusal above. A desired file whose `CREATE TABLE` declares `INHERITS` is refused before planning runs anything (`ErrDesiredInherits`), because building it would lock the live parent and add an inheritance edge to it. `diff` and `migrate --desired` report it as an `unsupported-statement` refusal with the `capability-boundary` class and exit 2. |
| Two index constraints declared the same way | A table can hold two `PRIMARY KEY`, `UNIQUE`, or `EXCLUDE` constraints with the same columns, `INCLUDE` list, predicate, operators, and deferrability when each was added by its own `ALTER TABLE`. One `CREATE TABLE` that declares both keeps only one of them, the primary key if either is one, and raises no error, and a desired file has no other way to declare the second. Export refuses such a table (`ErrUnrenderableMergedConstraints`). A desired file that declares both fails its build instead of planning the live copy of that constraint away (`ErrDesiredConstraintMerged`). The error names the constraint the server left out, or, when the earlier of the two is unnamed and takes the other's name, says the table holds one constraint fewer than the file declares, counting those a `LIKE ... INCLUDING INDEXES` clause copies; `migrate --desired` reports it as an `unsupported-statement` refusal with nothing run. That holds only when the table exists: for an absent table there is no scratch build, so the create path finds the missing constraint only after its `CREATE TABLE` commits, and fails with `create-name-mismatch`, leaving the table in place. Declare the rule once, and drop the live duplicate deliberately through `migrate --alter`. |
| Desired statements the server rejects | Planning builds an existing table's desired file on a scratch schema, so a statement the server rejects as written, such as an index on a column the file does not declare, a default that calls a function the schema lacks, or an unknown collation, is refused before anything runs (`ErrDesiredStatementRejected`, `unsupported-statement`, exit 2). A new table is built there only when its file declares a foreign key. Any other new table's file goes to the create path, which meets the statement when it runs: its `CREATE TABLE` commits first, and the failing statement leaves the table in place. Correct the file and plan again. |
| Server-chosen check constraint names | The numbering is not managed. PostgreSQL names an unnamed check constraint `<table>_<column>_check` when it reads exactly one column and `<table>_check` otherwise, and adds a number (`<table>_check1`, ...) when another constraint in the schema already holds that name, so the same checks can carry different names on a table built by a history of statements and on one built from the file. A check the file declares without a name is matched to a live check by definition, so the numbering alone plans nothing. A new unnamed check is added under its generated name, or the next free number when a kept check holds it. When that number would need the server to shorten the table or column part of the name to fit 63 bytes, the plan refuses with `ErrUnsupportedChange`: name the check in the file. When a `LIKE` clause could copy constraints, checks are matched by name. |
| Unlogged tables | Persistence is not managed: converging it (`SET LOGGED` / `SET UNLOGGED`) is a full table rewrite. Export refuses an unlogged table — a plain `CREATE TABLE` baseline would silently change its crash-safety and replication behavior — and a persistence mismatch between live and desired is a typed refusal from `diff` and `migrate --desired` (`not-native-safe-rewrite-required`, `capability-boundary`, exit 2), never a zero diff. |
| Table and column comments | Comments are metadata outside the table-shape model. Desired files and exports do not carry them; manage them with owner tooling. |
| Storage parameters (`fillfactor`, etc.) | Modeled, exported, and compared, but not converged. `pull` writes a table's storage parameters, its TOAST table's included, back as a `WITH (...)` clause on the `CREATE TABLE`, and a desired file that declares the live parameters plans its other changes normally. Boolean values compare by meaning, so a live `off` matches a declared `false`. Any other difference between live and desired is a typed refusal from `diff` and `migrate --desired` (`no-online-safety-problem`, owner `direct-operator`, exit 2), never a zero diff: change the parameters with owner tooling (`ALTER TABLE ... SET (...)`), then declare them in the file. A table with no text-like column has no TOAST table and the server discards `toast.*` parameters on it, so a file that adds such a column together with a `toast.*` parameter refuses too. The reverse also happens: a table keeps its TOAST table after its last text-like column is dropped, so export refuses `toast.*` parameters on a table with a dropped column and no remaining unbounded text-like column (`ErrUnrenderableToastOptions`) rather than write a baseline whose build would discard them. That refusal is export's alone; a row-security apply builds nothing from the table and is not refused by it. A row-security file is compared like any other desired file, so on a tuned table it declares the live `WITH (...)` clause too. |
| Identity and serial sequence declarations | Modeled and compared, but not converged. An identity whose sequence is declared away from the defaults (`START WITH`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `CACHE`, `CYCLE`) exports with its options clause, and a file that states the live declaration plans its other changes normally; any difference between live and desired is a typed refusal from `diff` and `migrate --desired` (`no-online-safety-problem`, owner `direct-operator`, exit 2). Change the declaration with owner tooling (`ALTER TABLE ... ALTER COLUMN ... SET ...`), then state it in the file. A serial cannot state a declaration, so export refuses a serial whose sequence is declared otherwise (`ErrUnrenderableSequenceOptions`), including an integer serial whose column was widened to `bigint` while its sequence stayed `integer`. That refusal is export's alone: a policy-only row-security apply goes ahead on such a table, because it renders nothing from the table. A serial's declaration is not compared either, so a file that writes the `serial` shorthand plans no change against a live serial whose sequence was tuned; the tuning stays as it is. Widening an identity column's type carries its sequence along, so a file that widens the column and states the declaration converges in one plan. A column whose default calls more than one sequence it owns is refused at render (`ErrMultipleOwnedSequences`), not at introspection, so planning other changes on the table still works. |
| Column collations | An explicit `COLLATE` on a column is exported and compared, but not converged: converging a collation delta rewrites the column and its indexes. Export writes the collation schema-qualified, so the baseline keeps the column's sort order and index semantics. A collation change is a typed refusal from `diff` and `migrate --desired` (`not-native-safe-rewrite-required`, `capability-boundary`, exit 2), and so is an added column that declares one (`unsupported-statement`). |
| Non-table objects | Views, materialized views, standalone sequences, enums, domains, extensions, functions, and triggers are outside the model. An enum type's labels are the exception: a desired file may hold one `CREATE TYPE ... AS ENUM` instead of a table (below). Within a table, a serial column's owned sequence is also managed: it round-trips through the `serial` pseudo-types — and ownership is verified through the catalog (`pg_depend`), so a hand-written `nextval` default on a standalone sequence that merely carries the serial-style name refuses rather than exporting as `serial` and silently privatizing a shared sequence. A column, check constraint, or index may *use* an unmanaged type or function (an enum, a domain, a SQL function) that the table's own schema or `public` defines. Planning resolves names in the order live introspection does, the table's schema and then `public`, so the definition round-trips whether the file names the object bare or qualified with its schema. An object in any other schema, such as an extension installed in `extensions`, is named qualified in the file by default; `--extension-schema` (Go: `DesiredSchema.WithExtensionSchemas`) adds schemas searched after those two, so a file can name such an object bare. In a file that declares row security they apply to the table definition only (Go: `DesiredWithRowSecurity.WithExtensionSchemas`); its policy expressions still name every such object qualified. Either way the file only uses the object: its own definition is not managed. |
| Enum types | A desired enum type file holds exactly one unqualified `CREATE TYPE ... AS ENUM` with distinct, non-empty labels; anything else in it, a table included, is refused by design. Only the labels converge: `diff` plans an `ALTER TYPE ... ADD VALUE` (kind `add-enum-value`) for each label the live type lacks, `BEFORE` the next live label when the file lists it ahead of one, and `migrate --desired` runs each through the imperative `ADD VALUE` path and re-plans to confirm the type converged. Adding a label locks only the type. PostgreSQL cannot drop or move a label, so a file that no longer lists a live label (removed or renamed) is refused with owner `direct-operator`, and one that lists the live labels in another order is refused by design. The type itself is not created: a type the schema lacks is refused (`enum-type-missing`, owner `direct-operator`), and a name that holds a domain, composite, range, or table row type is a `capability-boundary` refusal. Each label commits on its own, so a run stopped partway keeps the labels before it; plan again before retrying. |
| Multiple tables per file | A desired file is single-table scoped: exactly one `CREATE TABLE` plus `CREATE INDEX` statements on it. Multi-table schemas are managed as one file per table. |
| Live tables with no desired file | Not in `diff`'s view: the diff is single-table scoped, so it never plans a `DROP TABLE`, and the imperative front door refuses the statement as unsupported. A reviewed drop runs through the Go API (`executor.ExecuteDropTable`). The set of tables a schema should contain is the whole-schema owner's to enumerate and reconcile — see [Deliberately operator-owned](capabilities.md#deliberately-operator-owned) for the catalog query and its exclusions. |
| Greenfield table creation | Reachable through desired-state execution (`migrate --desired` or `migrate.RunDesired`): a plan whose table does not exist routes to the executor create path (`executor.ExecuteCreate`). Planning refuses every clause that binds to an existing object the absence proof does not cover (`PARTITION OF`, `INHERITS`, `LIKE`, and `OF`), plus `IF NOT EXISTS` and duplicate claimed relation names. Apply re-checks the same shape rules before anything executes. `CONCURRENTLY` is refused upstream at desired-file parse (`statement.ParseDesired`); the create path's admission re-checks it as defense in depth. |
| Changed stored generated column expression | Planned, never executed. `diff` plans the change as one `ALTER TABLE ... ALTER COLUMN ... SET EXPRESSION AS (...)` statement of kind `set-generated-expression`, refused as `unsupported-statement`: it recomputes every row under an `ACCESS EXCLUSIVE` lock, and no online path exists yet. Planning it this way, rather than as a drop and re-add of the column, leaves indexes on the column out of the plan. `SET EXPRESSION` needs PostgreSQL 17 or later; on older servers the plan still shows it, refused, and the only path is to drop and re-add the column, which also drops its indexes. A change to a generated column's type still fails the diff. |
| Virtual generated columns (PostgreSQL 18+) | Not modeled. A desired file cannot declare `VIRTUAL`, export refuses a live virtual column (`ErrUnrenderableVirtual`), and a desired file that declares the column any other way fails the diff, so a virtual expression is never converged as a column default. |
| Changed index or constraint definition | A redefinition diffs to drop-and-recreate, the drop is destructive, and desired-state execution refuses a plan containing a destructive statement — the whole plan, including the harmless recreate — unless the run pins the reviewed plan's fingerprint and names the table in the destructive acknowledgement (`--expect-fingerprint` with `--allow-destructive SCHEMA.TABLE`, or `DesiredRequest.ExpectedFingerprint` with `DesiredRequest.AllowDestructive`); the plan then runs as one reviewed unit, the drop of an index as `DROP INDEX CONCURRENTLY`. A partitioned table's index has no concurrent drop, so its plan stays refused unless the run also accepts the blocking lock with `--accept-blocking SCHEMA.TABLE` (`DesiredRequest.AcceptBlocking`) and an explicit `--statement-timeout` longer than `--lock-timeout`: the plain `DROP INDEX` then runs in one engine-owned transaction under those budgets, locking the parent, every partition, and every partition's index, and the run ends `executed-without-online-safety` (exit 3) ([desired file](lock-budgeted-passthrough.md#a-partitioned-tables-index-dropped-from-a-desired-file)). Alternatively drop it first with the plain `DROP INDEX` under `migrate --alter --accept-blocking --allow-destructive`, then rerun. A changed standalone index, primary key, unique constraint, or check constraint is replaced in place instead, keeping the old index or rule until the new one is installed ([capabilities](capabilities.md)). The drop of a changed standalone index reads its replacement again on the dropping session and refuses with `replacement-index-drift`, dropping nothing, if the replacement was dropped, left invalid, or rebuilt with another definition since planning. A replacement that stopped after its build resumes there: a valid `<name>_new` with the desired definition is used, not built again. A primary key replaced in place while the diff drops a `NOT NULL` the old key covered is swapped first, and the `NOT NULL` is dropped after the swap, since the old key owns it until then. A primary key or unique constraint a foreign key references is refused at plan time with `referenced-index` whenever the plan would drop it, so the plan does not fail at execution after its earlier statements committed. An index whose name alone changes is renamed with `ALTER INDEX ... RENAME TO` and never stops serving; execution reads it again under the table's `SHARE UPDATE EXCLUSIVE` lock and refuses with `renamed-index-drift`, renaming nothing, if it now backs a constraint or no longer has the definition the plan matched it by. A unique index or unique constraint replaced by a unique object of the other kind or under another name, and a constraint the file declares again under another name, are built first and the old one dropped after, so the guarantee holds throughout and a failed build leaves the old one standing. Under the same name, the new index is built as `<name>_new`, the old object is dropped, and the new index is renamed to the name or attached to the constraint; the drop reads `<name>_new` again under its lock and refuses with `replacement-index-drift`, dropping nothing, if it was dropped, left invalid, or rebuilt with another definition since planning. The plan still drops before it creates for a key or foreign key on a partitioned table, any other change of constraint kind, such as a unique constraint becoming a primary key, and a diff that also retypes a column or drops one beside an added column that may rewrite the table. In those plans a unique index or constraint lacks the old guarantee between the two statements, and the create fails if duplicates arrive in that window. A diff that only drops a column replaces first and drops the column last, and a check constraint on a partitioned table is replaced in place. To keep the guarantee throughout, create the replacement first with `migrate --alter`, then run the reviewed plan, which then only drops the old one ([the commands](execute-and-introspect.md#why---desired-and---alter-treat-the-drop-differently)). A new constraint that takes the name of a live unique index is refused, rather than run with the key unguarded, when the file renames that index (`renamed-index-name`) or when another unique index the plan builds takes over its key, with or without a predicate (`moved-unique-rule`): apply the rename or the new index first, then the constraint. One shape is not a redefinition: a new primary key or unique constraint whose name and index match a live unique index takes that index over with `ADD CONSTRAINT ... USING INDEX`, so the table keeps its guarantee and its index throughout. A primary key's columns are set NOT NULL online first. The statement names only the index, so execution reads the index again under the table's lock and refuses with `adopted-index-drift`, attaching nothing, if it was dropped, replaced under the same name, or left invalid since planning. A deferrable constraint takes the index over with its declared deferrability. An unfinished index build and a partitioned parent keep the drop and rebuild. A live constraint left `NOT VALID` with the desired definition is not a redefinition either: it plans as one `VALIDATE CONSTRAINT`, which runs for a foreign key the same way. The statement names only the constraint, so execution reads it again under the validation's own lock and refuses with `validated-constraint-drift`, validating nothing, if it was dropped or replaced under the same name since planning. |

## What desired-state execution converges today

Desired-state execution (`migrate --desired` or `migrate.RunDesired`) feeds
every planned statement back through the same gates as the imperative
front door, so the outcome of an ordinary desired-file edit is the
composition of the model boundaries above with those gates. At a glance:

| Desired-file edit | Outcome today |
| --- | --- |
| A desired file whose table does not exist yet | Converges — the greenfield create path verifies the table name and every relation name the desired file states (explicit index names and first-choice constraint-index and column-sequence names) are free and the role holds `CREATE` on the schema, then runs the `CREATE TABLE` and index builds as brief bounded steps. Names the server invents rather than names the desired file states are outside this coverage. An occupied claimed name is a typed `create-collision` refusal before anything runs — drop or rename the occupant, name a constraint's index explicitly, or for a sequence use an explicitly named sequence or a non-serial column. Duplicate-name SQLSTATEs backstop races for explicit names; for server-chosen names, the probe narrows the race to the time-of-check window, and after the `CREATE TABLE` commits the executor reads the constraint-index and sequence names the table actually owns and compares them against the claimed first-choice names — a name taken inside the window makes the server pick a suffixed replacement, which surfaces as a typed `create-name-mismatch` failure at step 1 with the born table left in place for an operator to rename the relation or drop, then re-diff (a read of the owned names that does not complete is the same step-1 failure as `create-names-unverified`, never a pass). Unsupported create shapes (`PARTITION OF`, `INHERITS`, `LIKE`, `OF`, `IF NOT EXISTS`) and duplicate claimed names refuse at plan time and are re-checked at apply. |
| Add a column | Converges. Runs as a bounded attempt of the submitted form. The table-size guard (below) skips it when the probe proves the column adds in place without reading the table, as for a nullable column or one with a constant default. |
| Widen a column type (`varchar(50)` → `varchar(255)`) | Converges — the same bounded attempt, under the same size guard. |
| Add an index | Converges via `CREATE INDEX CONCURRENTLY`. Not size-guarded: long online work on a large table is the pattern's purpose. |
| Rebuild an index left invalid by an unfinished concurrent build | Plans as the same `create-index` change — the invalid entry, though it carries the desired name and definition, does not deliver the index, and the diff never emits a drop for it. The plan report says so alongside the statement: an `invalid-index-rebuild` [advisory](plan-report.md#advisory-kinds-advisorieskind-diff-source-only) names the entry, so the create is not mistaken for a plain new index. Execution then meets the occupied name and stops by proof: a `failed` outcome carrying `invalid-index-abandoned` (the invalid-index row above); remove the leftover per the [runbook](invalid-index-recovery.md), or, as a library caller, run the create through `executor.RebuildAbandonedIndex`, and rerun. A build still in progress looks the same to the diff (`indisvalid` stays false until the build's final wait ends) and plans the same create and advisory; execution then stops with `invalid-index-build-in-flight` rather than build twice. |
| Remove or redefine an index that is currently invalid | The diff leaves the invalid entry alone: it never emits a drop for an entry that may be someone's build still running, so `diff` plans no statement for a removed index and only the `create-index` for a redefined one (execution then meets the occupied name as in the row above). The plan is not silent about it: an [advisory](plan-report.md#advisory-kinds-advisorieskind-diff-source-only) names the entry the diff left in place — `invalid-index-undeclared` when the desired file no longer names the index, `invalid-index-rebuild` when it redefines it under the same name — so an empty plan over such a table reads as "no changes to run", not as converged. This also means the `_ccnew` leftover of an interrupted `REINDEX ... CONCURRENTLY`, which no desired file names, does not block the table's other changes; clear it per the [runbook](invalid-index-recovery.md). On a partitioned parent, an invalid index is a partitioned index build that did not finish: when its definition is the desired one, the diff plans the same `CREATE INDEX` again, which the build resumes, and no advisory is raised. |
| Add a constraint (`UNIQUE`, `CHECK`); `SET NOT NULL` | Converges via the safer online sequence; not size-guarded either. |
| Relax a `NOT NULL`, drop a column, drop a constraint, drop an index | Refused, whole plan, unless the run pins the reviewed plan's fingerprint and names the table in the destructive acknowledgement: each is destructive, because it discards a guarantee, structure, or data. With `--expect-fingerprint` (the `sha256:...` value `diff --desired` prints) and `--allow-destructive SCHEMA.TABLE`, every destructive statement of the plan runs under that acknowledgement as it does on `migrate --alter`: it is audited, and its verdict carries `allowed_destructive: true`. A dropped index runs as `DROP INDEX CONCURRENTLY`, never taking the table's blocking lock, and is read again on the session that drops it; an index of a partitioned table, which has no concurrent drop, stays refused unless `--accept-blocking SCHEMA.TABLE` also names the table, and then runs as the plain `DROP INDEX` under the run's budgets, locking the parent, every partition, and every partition's index. Without the acknowledgement the refusal names the fingerprint to pin and the table to name. On a partitioned parent a column or constraint drop removes the column or constraint from every partition, sub-partitions included, since a partition's columns and inherited constraints are the parent's; the column drop locks the whole tree first and fails, dropping nothing, with `dropped-column-partition-key` for a partition key column at any level (the planner already refuses one it plans, with `partition-key`) and with `dropped-column-partition-dependent`, naming the objects, when a partition carries an index, constraint, statistics object, or sequence of its own on the column, which the plan did not review: drop or change it first, then re-plan. A `NOT NULL` drop on a partitioned parent, and a column, constraint, or `NOT NULL` drop on a table with inheritance children, fails with `dropped-object-has-descendants`; make it with `migrate --alter` after reviewing what it removes from each table below. `migrate --alter` checks no partition's own objects: the statement the operator wrote drops them with the column, as it drops the table's own. |
| Change an index or constraint definition | The drop-and-recreate row above: refused, whole plan, until the run carries the pin and the acknowledgement. |
| Narrow a column type (`varchar(255)` → `varchar(50)`) | Converges through copy-and-swap: the plan's disposition is `execute` with the statement routed to the `copy-and-swap` backend, and desired-state execution runs it with the same preflight gates as `migrate --alter` (the Copy-and-swap row above), always on the live path. The route is in preview: a desired-state run without `--copy-and-swap` (`CopySwapOptions.Enabled`) refuses the whole plan `copy-and-swap-refused` with cause `copy-and-swap-not-enabled` at admission (after planning has read the catalog, before the preflight reads anything), nothing executed; the result's `cause` carries the token. The route's preflight is read at admission too, before any statement runs, so a table or server the route refuses — no `--free-disk`, no logical decoding (desired-state execution rejects `--block-writes`, so it never takes the table offline for writes), a trigger, a dependent view — refuses the whole plan with nothing executed, native statements included. `diff` does not read the preflight — its plan report says `execute` on the route alone, and whether the route can run here, now, with these flags, is answered when the plan is executed. `migrate --desired --dry-run` reads one part of it: when the table is a partitioned parent, a partition, or a member of an inheritance tree, the dry run ends in the run's whole-plan refusal, cause `copy-and-swap-partitioned` (`copy-and-swap-unlogged` or `copy-and-swap-force-rls` instead when the table is also UNLOGGED or forces row security, which the preflight decides first), exit 2, in place of the plan; every other preflight refusal is answered when the plan is executed. A plan that retypes two columns runs two copy-and-swap passes on the table, one per statement; the second replaces the done row the first leaves behind. |
| A bounded-attempt edit on a table above the size threshold | Refused at that statement (`not-native-safe-table-too-large`): with the default 1 GiB threshold, widening a column type on a larger table refuses until the threshold is raised. A statement whose every operation is proven catalog-only is not refused. |

A destructive refusal is all-or-nothing: one destructive statement refuses
the whole plan, and the non-destructive statements beside it do not run —
the refusal detail says how many were skipped.

The size threshold is policy, not capability: `Options.MaxTableSizeBytes`
(the CLI's `--max-table-size`) defaults to 1 GiB, and the guard covers only
the blind bounded attempt of a submitted form — planner-proven online
sequences, and statements made only of proven catalog-only operations, are
exempt. On a table you operate deliberately, raising the
threshold is the sanctioned way to converge the bounded-attempt edits; the
refusal means pg-sprite cannot prove the change is instant at that size,
not that the change is unsafe. Why the guard covers exactly that path —
and why the wrong-guess cost scales with table size — is
[optimistic-attempt.md](optimistic-attempt.md).
